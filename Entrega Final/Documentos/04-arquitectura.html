1. Arquitectura y modelo de datos

1.1 Arquitectura general

Cliente y servidor permanecen separados y se comunican exclusivamente mediante peticiones HTTP con formato JSON y autenticación por token. Esa separación permite desplegar la interfaz en una red de distribución de contenidos y el servicio junto a su base de datos, que es el esquema de producción adoptado.

1.3 Interfaz de programación

Tabla 15. Principales puntos de acceso
MétodoRutaFunción
POST/api/auth/registerCrear una cuenta.
POST/api/auth/loginIniciar sesión y emitir el token.
GET/api/animales/publicosCatálogo público, sin sesión.
GET/api/animales/miosMascotas del usuario autenticado.
GET/api/animalesTodas las mascotas; reservado al rol administrador.
POST/api/animalesRegistrar una mascota.
PUT/api/animales/:idEditar, previa verificación de propiedad.
DELETE/api/animales/:idEliminar, previa verificación de propiedad.
GET/api/modelos3d/catalogo/:categoriaModelos disponibles para una especie.
POST/api/modelos3d/:id/derivarCrear una copia personalizada del modelo.
POST/api/uploads/imagenSubir una fotografía al servicio externo.
GET/api/healthEstado del servicio y de la base de datos.
Decisión de diseño. Las rutas /api/animales/mios y /api/animales son distintas de forma deliberada: el servidor decide qué puede ver cada rol. Filtrar en la interfaz habría implicado enviar al navegador información que el usuario no debe poseer.
