# Aplicación de Scrum

## 1. Enfoque

Scrum se utilizó para organizar el producto en metas cortas, inspeccionar incrementos y adaptar el backlog. Al tratarse de un proyecto académico con un responsable principal, se documenta una adaptación de roles sin afirmar reuniones o participantes que no hayan sido registrados.

## 2. Pilares de Scrum

| Pilar | Aplicación en Mascotas 3D |
| --- | --- |
| Transparencia | Backlog, criterios de aceptación, estados y riesgos están documentados. |
| Inspección | Cada sprint termina con compilación, revisión funcional y demostración. |
| Adaptación | Los problemas visuales, de ubicación, permisos y exportación originaron ajustes del backlog. |

## 3. Valores

- **Compromiso:** completar una meta verificable por sprint.
- **Enfoque:** priorizar el flujo de búsqueda antes de mejoras decorativas.
- **Apertura:** registrar limitaciones como servicios externos o modelos sin UV.
- **Respeto:** proteger datos del propietario y facilitar una interfaz clara.
- **Coraje:** reemplazar soluciones insuficientes, como pintura flotante, por pintura UV.

## 4. Responsabilidades

| Responsabilidad Scrum | Aplicación académica |
| --- | --- |
| Product Owner | Mantiene la visión, prioriza el Product Backlog y valida valor. En la adaptación, estas actividades son asumidas por el responsable del proyecto con retroalimentación académica. |
| Scrum Master | Facilita el proceso, identifica impedimentos y protege la meta del sprint. En la adaptación, se registra mediante seguimiento y retrospectiva. |
| Developers | Diseñan, implementan, prueban y documentan el incremento. Responsable técnico: Bryan Quispe. |
| Stakeholders | Docente, evaluadores y usuarios de prueba que proporcionen retroalimentación real. |

## 5. Eventos

| Evento | Propósito | Evidencia esperada |
| --- | --- | --- |
| Sprint | Contenedor temporal del incremento. | Meta, backlog, incremento y resultado. |
| Sprint Planning | Definir por qué, qué y cómo se trabajará. | Meta y Sprint Backlog. |
| Daily Scrum | Revisar avance y ajustar el plan diario. | Registro breve de avance, siguiente acción e impedimentos. |
| Sprint Review | Inspeccionar el incremento con interesados. | Funciones demostradas y cambios solicitados. |

| Artefacto | Compromiso | Uso en el proyecto |
| --- | --- | --- |
| Product Backlog | Product Goal | Lista priorizada de capacidades del producto. |
| Sprint Backlog | Sprint Goal | Historias y tareas seleccionadas para el sprint. |
| Incremento | Definition of Done | Software integrado, verificable y documentado. |

## 7. Definition of Ready

Una historia puede ingresar a un sprint cuando:

- Expresa actor, necesidad y beneficio.
- Tiene criterios de aceptación comprobables.
- Sus dependencias están identificadas.
- Tiene prioridad y estimación.
- Es suficientemente pequeña para el sprint.
- No depende de una decisión crítica sin resolver.

## 8. Definition of Done

Una historia se considera terminada cuando:

- La implementación está integrada.
- TypeScript compila sin errores.
- Los permisos y validaciones relevantes funcionan.
- El flujo principal fue probado.
- La interfaz no presenta desbordamientos evidentes en escritorio o móvil.
- No se exponen secretos ni ubicación exacta.
- La documentación afectada fue actualizada.
- El incremento puede demostrarse desde la interfaz.

## 9. Gestión de cambios

Los cambios se incorporan al Product Backlog, se priorizan por valor, riesgo y dependencia, y se seleccionan en una planificación posterior. Un defecto crítico de seguridad puede interrumpir el trabajo si impide cumplir la Definition of Done.
